# 🛠️ Problem Learning Coach (problem-learning-coach)

> **拒绝巨婴，拒绝玩具代码。把大模型重塑为“只给极品图纸、逼新人动手折腾”的工业级技术导师。**

---

## 🚨 为什么发明这个项目？

在生成式 AI 时代，市面上 99% 的 Prompt 都在卷“如何让 AI 替人写更多、更复杂的代码”。但我们忽略了一个残酷的现实：**“能生成代码”不等于“能教会新人”**。

当 AI 吐出几百行充斥着设计模式、异步回调和底层网络优化的复杂代码时，新人往往会面临以下三个灾难：
1. **无脑 Copy 流**：大体看得懂，但卡在局部核心机制上不敢乱动，直接 `Ctrl+C / Ctrl+V` 进生产环境，跑通靠运气，跑崩埋下线上雪崩的雷。
2. **玩具代码应付生产**：普通 AI 极易给出“简易版”Demo（例如基于 `inputStream.read()` 然后直接 `split("\n")` ）。新人分不清什么是玩具，什么是生产级，直接照抄导致线上高频设备流发生粘包、半包、脏数据入库。
3. **搞脏 Git 工作区**：某些全自动 Agent 为了跑 Demo，在本地乱建临时工程、下载一大堆依赖，甚至越权篡改了原项目的核心生产配置。

**`problem-learning-coach` 就是为了终结这一切而生的。** 它不碰源码，通过一套极其严密的、卡点分明的**纯文本沙盒机制**和**企业级合规质检**，逼着新人在绝对安全的 Markdown 文档里“建立心理模型 $\rightarrow$ 手动复刻图纸 $\rightarrow$ 自己折腾环境”，实现真正的深度学习和高标准出活。

---

## 💎 核心设计理念与冷酷铁律

本框架之所以能彻底解决“AI 代码看不懂、不敢抄、容易崩”的大问题，是因为它在底层焊死了以下几条硬性约束：

### 1. 🛑 绝对零污染（Hard Safety Rule）
AI 在执行教学时，原项目源码只读。**严禁在本地创建任何 Demo 文件夹、脚本或实体代码文件。** 所有的最小化 Demo 必须以**纯文本代码块**的形式，追加（Append）在唯一的交付文档 `docs/learn/Lyyyyymmdd(主题).md` 中。Git 工作区绝对干净。

### 2. 🚼 拒绝巨婴，必须学会折腾（No Scaffold Provide）
本框架在图纸层面极其慷慨（每一行代码配置都有因果注释），但在动手层面极其冷酷。**AI 绝对不会提供任何一键初始化的脚手架命令或自动化构建脚本。** 新人想要看效果，必须自己开一个空文件夹，自己去配开发环境、自己调编译器、自己处理本地报错、自己把代码块一块块粘过去补全。**如果连这点折腾的能力都没有，那根本不配做工程师。**

### 3. 🛡️ 降维打击：企业级规则硬核质检（Enterprise-Grade Judgment）
拒绝任何敷衍的、单文件的玩具 Demo。如果教学的主题涉及物联网/工业互联网、二进制协议（如 NMEA、RTCM）、网络通信（Netty/MQTT）、高并发中间件、数据库事务或资金安全等高风险领域，AI 必须：
* 先对齐行业标准，对当前项目的既有代码进行**“企业级规则判断”**（符合/部分符合/不符合）。
* 如果原项目写得规范，Demo **绝对不准简化**关键的安全/可靠性边界（如必须保留“断帧 $\rightarrow$ Checksum校验 $\rightarrow$ 业务解码”的三层隔离）。
* 如果原项目本身是屎山，AI 会**先忠实复刻现状（让新人看懂当前代码），紧接着甩出 `企业级补强方案`**，降维打击玩具代码。

### 4. 📝 全语句逐行注释铁律（Line-by-Line Commentary）
在 Demo 代码块中，每一行有效的执行语句、配置声明、依赖引入上方，必须紧跟一条中文注释。注释不允许只写标签，必须说明：**“这一行是干什么的”**、**“为什么要配在这里”** 以及 **“如果删掉或配错会引发什么严重后果”**。把老工程师几十年的隐性踩坑经验强制显性化。

## 🔄 阶段式交互心流（Execution Phases）

框架将 AI 与新人的交互强行拆分为三个严格演进的阶段，采用“通关挂起”机制，彻底杜绝大模型长文本断流或抢跑偷懒：

[阶段一：讲解原理] ──> (生成宏观架构/因果链/核心代码) ──> 🛑 触发【学习重点确认】并卡点挂起
│
[阶段二：学习最小化demo] <── (在MD中追加100%完整的纯文本图纸) <─── 用户回复确认重点
│
└─> 新人对照图纸，在本地独立文件夹中【手动折腾、复刻运行、肉眼对齐控制台日志】
│
[阶段三：追加学习] ──> (用户输入追加学习 XXX) ──> 在同文档末尾以 Append 方式纵向滚雪球扩展

## 📂 导出的学习文档标准骨架（Output Shape）

每一个被本框架驯化后生成的文档，都是一份躺在项目文档目录里、随时可以拿来当积木参考的顶级图纸。其严格遵循以下结构：

```markdown
# 标题（规范命名：Lyyyyymmdd(主题).md）

> 目标读者：刚入职的新人 / 想要理清该局部的开发者
> 阅读目标：彻底搞懂 XXX 机制并在独立沙盒中参考复刻

## 1. 一句话讲清楚
## 2. 这个问题在项目里是什么
## 3. 架构和流程（必须包含高可读性的 Mermaid 拓扑图）
## 4. 当前设计的好处
## 5. 潜在不足和坑
## 6. 类似设计推荐
## 7. 核心代码以及注释（原项目只读引用）
## 8. 接口或运行说明
## 8. 学习重点确认 🛑（AI 在此行切断输出，等待新人选择 2-5 个基于上下文的定制重点）

------------【以下为新人确认重点后，AI 纵向追加的内容】------------

## 9. 最小化demo（关于XXX）
## 9.1 demo 技术栈和完整性说明（明确拒绝本地运行，声明本地折腾边界）
## 9.2 企业级规则判断（针对该领域的硬核 Checklist 质检报告）
## 9.3 基于 demo 的架构图
## 9.4 按开发顺序展示文件内容（标明【所属路径】，提供行行带后果的中文注释）
## 9.5 手动运行命令、预期结果和原项目对应关系（提供预期日志供新人肉眼 Diff）
## 9.6 做足的地方和不足（主动戳破 Demo 的幻觉，划清生产边界）
## 10. 下次遇到怎么判断

## 11. 追加学习：YYY（支持无限续杯，顺着新人的衍生盲区一路Append扩展）
## 12. 最小化demo（关于YYY）


```

## 🚀 如何使用？

1. 在你的项目根目录下创建 `.cursorrules`、`SKILL.md` 或者直接将其作为系统提示词（System Prompt）常驻在你常用的 AI 助手（如 Gemini, Cursor, Claude）中。

2. 将本项目提供的 `problem-learning-coach` 提示词全文复制进去。

3. 当新人对项目里的某段晦涩逻辑（如：Dio 拦截器 401 刷新、Kafka 幂等消费、NMEA/RTCM 协议断帧等）看不懂时，直接对 AI 发起提问：

   > *“帮我用 problem-learning-coach 梳理一下这段代码的逻辑，我想生成一份学习文档。”*

4. 顺着 AI 的阶段提示，开启硬核的图纸复刻学习之旅。
